Для AI-Breadboard я бы спроектировал в `apps\windows\sdk` отдельный Deep Software Scanner — сканер установленного программного обеспечения, который запускается по требованию и собирает следы программ по всей Windows, включая давно не запускавшиеся приложения, остатки удалённых программ, пользовательские профили, реестр, службы и задачи планировщика.

Главное отличие от обычного списка установленных приложений: сканер должен обнаруживать не только зарегистрированные программы, но и фактические следы их существования. Приложение может отсутствовать в списке «Установленные приложения», но оставлять каталоги, исполняемые файлы, службы, записи автозапуска и конфигурацию.

Я бы разделил задачу на три уровня:

* Быстрое обнаружение — источники установленных приложений, реестр, службы и автозапуск.

* Глубокое сканирование по требованию — обход каталогов, поиск исполняемых файлов, анализ метаданных, конфигураций и остатков.

* Корреляция следов — объединение найденных объектов в одну карточку программы с оценкой уверенности, активности и полноты удаления.

При этом сканер должен работать в режиме read-only: ничего не удалять, не запускать найденные программы и не изменять настройки ОС.

## 1. Где Windows-программы оставляют следы

### 1.1. Каталоги установки и пользовательские каталоги

Системные и общие каталоги установки

Приоритет: высокий

* `C:\Program Files\`

* `C:\Program Files (x86)\`

* `%ProgramW6432%`

* `%ProgramFiles(x86)%`

* `%ProgramData%`

* `C:\Program Files\Common Files\`

* `C:\Program Files (x86)\Common Files\`

Здесь находятся приложения, библиотеки, общие компоненты, служебные файлы и каталоги обновления.

Пользовательские приложения

Приоритет: очень высокий

* `%LOCALAPPDATA%\Programs\`

* `%LOCALAPPDATA%\`

* `%APPDATA%\`

* `%USERPROFILE%\AppData\Local\Programs\`

* `%USERPROFILE%\AppData\Local\Packages\`

* `%USERPROFILE%\AppData\Roaming\`

Здесь часто располагаются приложения, установленные без прав администратора, пользовательские сборки, плагины, профили, обновления и остатки удалённых программ.

Другие места установки

Приоритет: высокий

* `%USERPROFILE%\`

* `%USERPROFILE%\Desktop\`

* `%USERPROFILE%\Downloads\`

* `%USERPROFILE%\Documents\`

* `%PUBLIC%\`

* Корни других локальных дисков: `D:\`, `E:\` и т. д.

* Пользовательские каталоги вроде `C:\Apps\`, `C:\Tools\`, `D:\Portable\`

Здесь встречаются portable-программы, распакованные архивы, самостоятельные сборки и приложения, которые не проходили стандартную установку.

Важный нюанс: `%APPDATA%` — это обычно `%USERPROFILE%\AppData\Roaming`, а `%LOCALAPPDATA%` — `%USERPROFILE%\AppData\Local`. Оба каталога нужно анализировать независимо: первый чаще содержит переносимые пользовательские настройки, второй — локальные данные, кэши, бинарные файлы и служебные компоненты.

Необходимо учитывать все локальные профили Windows, а не только текущий. Для этого сканер может получать список профилей через `Win32_UserProfile` и проверять доступность их каталогов. Профили других пользователей, зашифрованные данные и защищённые каталоги следует помечать как частично доступные, а не объявлять пустыми.

### 1.2. Каталоги, где остаются настройки и данные программ

Это один из важнейших этапов глубокого сканирования: программа может быть удалена из каталога установки, но её данные продолжат существовать.

| Каталог                                                | Что искать                                                    |
| ------------------------------------------------------ | ------------------------------------------------------------- |
| `%APPDATA%`                                            | Профили, настройки, расширения, плагины, конфигурации         |
| `%LOCALAPPDATA%`                                       | Локальные базы, кэши, бинарные файлы, обновления              |
| `%LOCALAPPDATA%\Temp\`                                 | Временные каталоги установщиков и распаковок                  |
| `%TEMP%`                                               | Остатки инсталляторов и обновлений                            |
| `%PROGRAMDATA%`                                        | Общие данные, сервисные компоненты, конфигурации              |
| `%USERPROFILE%\.config\`                               | Настройки кроссплатформенных приложений                       |
| `%USERPROFILE%\.cache\`                                | Кэши, иногда содержащие следы давно не запускавшихся программ |
| `%USERPROFILE%\.local\`                                | Данные и исполняемые файлы некоторых портированных приложений |
| `%USERPROFILE%\.ssh\`                                  | Конфигурация SSH-клиентов и сопутствующие файлы               |
| `%USERPROFILE%\.vscode\`                               | Данные VS Code, расширения и настройки                        |
| `%APPDATA%\Microsoft\Windows\Start Menu\Programs\`     | Ярлыки приложений                                             |
| `%PROGRAMDATA%\Microsoft\Windows\Start Menu\Programs\` | Общесистемные ярлыки                                          |

Последние каталоги с точками в именах — это условные примеры, а не обязательные системные папки. Сканер должен находить их, если они существуют.

### 1.3. Реестр Windows

Реестр необходимо анализировать независимо от файловой системы. Запись может сохраниться после удаления файлов программы, а исполняемый файл может располагаться в совершенно другом каталоге.

| Раздел                                                                 | Что обнаруживать                                        |
| ---------------------------------------------------------------------- | ------------------------------------------------------- |
| `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall`             | Зарегистрированные системные программы                  |
| `HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall` | 32-битные приложения на 64-битной Windows               |
| `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall`             | Программы текущего пользователя                         |
| `HKCU\Software\`                                                       | Настройки и идентификаторы приложений                   |
| `HKLM\Software\`                                                       | Общесистемные настройки и компоненты                    |
| `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`                   | Пользовательский автозапуск                             |
| `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`                   | Общесистемный автозапуск                                |
| `HKLM\SYSTEM\CurrentControlSet\Services`                               | Службы и драйверы                                       |
| `HKLM\SOFTWARE\Classes\`                                               | COM-компоненты, обработчики файлов и другие регистрации |
| `HKCU\Software\Classes\`                                               | Пользовательские регистрации COM и ассоциаций           |
| `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths`             | Пути к исполняемым файлам                               |

Дополнительно стоит проверять разделы Explorer Shell Extensions, AppInit DLLs, зарегистрированных обработчиков протоколов и расширений оболочки. Некоторые из них требуют особой осторожности: их наличие не обязательно означает, что компонент установлен неправильно или не используется.

Сканер должен учитывать обе разрядности реестра, пользовательские hive-файлы и доступные SID профилей. Нельзя считать отсутствие записи в одном представлении доказательством отсутствия программы.

### 1.4. Службы, драйверы и задачи планировщика

Программа может давно не запускаться в интерактивном режиме, но её фоновый компонент продолжает работать или ожидает события.

| Источник                   | Интерфейс обнаружения                                         |
| -------------------------- | ------------------------------------------------------------- |
| Windows Services           | SCM API, `Win32_Service`, `Get-CimInstance Win32_Service`     |
| Драйверы                   | SCM, `Win32_SystemDriver`, сведения о загруженных модулях     |
| Task Scheduler             | COM API, `schtasks /query /fo CSV /v`                         |
| Автозагрузка пользователя  | Папки Startup, реестр, ярлыки                                 |
| Общая автозагрузка         | `%ProgramData%\Microsoft\Windows\Start Menu\Programs\Startup` |
| WMI event subscriptions    | WMI/CIM и связанные постоянные подписки                       |
| COM registration           | Реестр, CLSID, ProgID, InprocServer32, LocalServer32          |
| Фоновые задания обновления | Планировщик, службы и записи обновляющих компонентов          |

Для каждого объекта нужно извлекать путь к исполняемому файлу, аргументы запуска, учётную запись или контекст выполнения, идентификатор владельца и состояние.

Это особенно полезно для обнаружения остатков: например, служба с путём к отсутствующему EXE — сильный признак неполного удаления.

## 3. Исполняемые файлы, библиотеки и метаданные

Глубокий сканер должен искать не только `*.exe`, но и другие типы файлов.

| Тип          | Примеры                                        | Зачем                                         |
| ------------ | ---------------------------------------------- | --------------------------------------------- |
| Исполняемые  | `.exe`, `.com`, `.scr`                         | Программы и запускаемые компоненты            |
| Библиотеки   | `.dll`, `.ocx`                                 | Модули и компоненты приложений                |
| Установщики  | `.msi`, `.msix`, `.appx`                       | Пакеты установки                              |
| Скрипты      | `.ps1`, `.cmd`, `.bat`, `.vbs`, `.js`          | Вспомогательные инструменты и запускатели     |
| Java         | `.jar`                                         | Приложения и инструменты Java                 |
| Python       | `.py`, `Scripts\`, `python.exe`                | Скрипты, окружения и инструменты              |
| Конфигурации | `.json`, `.yaml`, `.ini`, `.toml`, `.xml`      | Идентификация приложения и его компонентов    |
| Манифесты    | `package.json`, `pyproject.toml`, `Cargo.toml` | Привязка проекта к установленным инструментам |

Не следует безусловно обходить каждый каталог в поисках каждого расширения. Например, миллионы `.dll` внутри системных компонентов и кэшей дадут много шума. Лучше использовать этапы: сначала каталог и метаданные, затем целевой поиск по интересующим признакам.

Для PE-файлов полезно извлекать:

* `CompanyName`, `ProductName`, `FileDescription`;

* `FileVersion`, `ProductVersion`;

* `OriginalFilename`;

* цифровую подпись и издателя;

* архитектуру x86/x64/ARM64;

* размер, время изменения и доступное время создания;

* хеш SHA-256 — по настройке или для выбранных кандидатов.

Для ярлыков `.lnk` нужно разрешать целевой путь и аргументы. Ярлык сам по себе не является установленной программой, но его цель может раскрыть portable-приложение или оставшийся путь.

## 4. Логи, кэши, история и косвенные следы

Эти источники особенно ценны при поиске давно не запускавшихся приложений.

* Журналы Windows: Application, System, журналы установщика MSI и доступные журналы AppX/Deployment.

* История установки и обновлений: записи деинсталляторов, логи установщиков, журналы пакетных менеджеров.

* Кэши загрузок: браузерные загрузки, кэши пакетных менеджеров и временные каталоги — только в пределах заданной политики.

* Prefetch: `%SystemRoot%\Prefetch\` может содержать свидетельства запуска EXE, если Prefetch включён и данные ещё сохранились.

* Amcache: сведения об обнаруженных приложениях и файлах, доступные через соответствующие механизмы Windows.

* Shimcache / AppCompatCache: данные совместимости, которые могут помочь в расследовании, но не являются надёжным журналом фактических запусков.

* Recent Items и Jump Lists: `%APPDATA%\Microsoft\Windows\Recent\` и связанные данные пользовательской активности.

* Windows Search index: может помочь найти имена и пути файлов, если индексирование включено.

* История PowerShell: иногда содержит команды запуска, установки или удаления.

* Карантин антивируса и журналы безопасности: только доступные метаданные, без попыток извлечь или запускать подозрительные объекты.

У этих источников разные ограничения. Например, наличие записи в Prefetch или Amcache не доказывает, что приложение запускалось недавно. А отсутствие записи не доказывает, что оно никогда не запускалось.

Я бы хранил такие сведения как evidence — доказательства обнаружения, с указанием источника, времени наблюдения и степени достоверности.

## 5. Как определить, что программа давно не запускалась

Здесь важно разделить четыре разных вопроса:

1. Установлена ли программа сейчас?

2. Остались ли от неё файлы или системные регистрации?

3. Есть ли доказательства того, что она запускалась?

4. Когда она запускалась в последний раз, если это вообще можно установить?

Ни один отдельный источник не отвечает на все четыре вопроса.

Предлагаю собирать признаки в отдельную карточку:

| Признак                    | Источник                                          | Достоверность                                                  |
| -------------------------- | ------------------------------------------------- | -------------------------------------------------------------- |
| Последний запуск процесса  | Телеметрия AI-Breadboard, если процесс наблюдался | Высокая в пределах периода наблюдения                          |
| История запусков           | Prefetch и другие артефакты                       | Зависит от источника                                           |
| Последняя модификация EXE  | Метаданные файловой системы                       | Низкая для определения запуска                                 |
| Запись деинсталлятора      | Реестр                                            | Высокая для наличия регистрации, не для фактического состояния |
| Путь службы                | SCM / реестр                                      | Высокая для существующей регистрации                           |
| Отсутствующий целевой EXE  | Служба, задача или ярлык                          | Сильный признак оставшейся ссылки                              |
| Остаточная папка           | Файловая система                                  | Слабый признак без дополнительных совпадений                   |
| Запись пакетного менеджера | Метаданные менеджера                              | Зависит от актуальности регистрации                            |

Не используй время последнего изменения файла как замену времени последнего запуска. Программа может запускаться каждый день, не меняя бинарный файл, или обновиться автоматически без пользовательского запуска.

## 6. Алгоритм глубокого сканирования

Я бы реализовал его как последовательность независимых проходов, которые можно запускать отдельно.

Deep Scan Controller

Запуск вручную, из консоли или через API

Registry Probe

Uninstall, Run, Services, COM

Filesystem Probe

Program Files, AppData, другие диски

Execution Evidence

Prefetch, журналы, история наблюдений

Package Probe

MSI, AppX, WinGet и другие менеджеры

Evidence Correlator

Сопоставление путей, имён, издателей, версий и хешей

Software Inventory + Telemetry DB

Программы, компоненты, следы, история и отчёт сканирования

### Рекомендуемые режимы

* `quick` — реестр, службы, задачи, пакеты и автозагрузка.

* `deep` — рекурсивный обход выбранных корней, поиск файлов и метаданных.

* `forensic` — дополнительно доступные журналы, Prefetch, Amcache и другие артефакты.

* `targeted` — анализ конкретного имени, пути, издателя или идентификатора программы.

* `orphans` — поиск несогласованных регистраций, отсутствующих файлов и остаточных каталогов.

`forensic` здесь означает сбор доступных артефактов, а не полноценную судебно-криминалистическую экспертизу. Чтение защищённых артефактов, offline hive-файлов и системных областей требует отдельной реализации и соответствующих разрешений.

## 7. Как встроить сканер в `apps\windows\sdk`

Я бы предложил такую структуру модулей — её можно адаптировать к уже существующему коду, не переписывая работающие части.

```
apps/
└── windows/
    └── sdk/
        └── software_scanner/
            ├── __init__.py
            ├── controller.py
            ├── models.py
            ├── scope.py
            ├── filesystem_probe.py
            ├── registry_probe.py
            ├── services_probe.py
            ├── tasks_probe.py
            ├── packages_probe.py
            ├── execution_evidence_probe.py
            ├── metadata_extractor.py
            ├── correlator.py
            ├── orphan_detector.py
            ├── report.py
            └── policies.py
```

Основная идея — не делать один огромный скрипт, который обходит всё подряд. Каждый `probe` должен возвращать стандартизированные записи о найденных объектах.

### Что хранить в `telemetry.db`

Я бы разделил данные на несколько сущностей:

* `software_inventory` — карточки обнаруженных программ;

* `software_components` — EXE, DLL, службы, задачи, плагины и другие компоненты;

* `software_evidence` — отдельные следы с источником и достоверностью;

* `software_scan_runs` — параметры, время начала и окончания, ошибки, статистика и статус сканирования;

* `software_activity` — история наблюдений активности, включая результаты существующих сенсоров;

* `software_relationships` — связи между приложением, установщиком, службой, каталогом и пакетами.

При повторном сканировании не нужно каждый раз создавать дубликаты всех объектов. Следы следует идентифицировать по устойчивым признакам, а изменения сохранять в истории наблюдений. Удалённый файл, например, должен превращаться в событие «больше не обнаруживается», а не уничтожать историю предыдущих сканирований.

## 8. Что особенно важно предусмотреть

1. Политика обхода. Список корней, исключений, максимальной глубины и разрешённых типов файлов должен быть конфигурируемым.

2. Контроль нагрузки. Ограничить параллелизм, частоту чтения и количество хешируемых файлов. Глубокое сканирование не должно создавать резкие пики дисковой нагрузки.

3. Пропуски доступа. Отдельно учитывать `Access Denied`, недоступные диски, reparse points, циклические ссылки и отключённые профили.

4. Защита от повторного обхода. Не переходить бесконечно по junction и symbolic links; исключить повторное сканирование одной и той же цели.

5. Приватность. Не собирать содержимое документов, пароли, токены и пользовательские секреты. Для конфигураций достаточно метаданных и ограниченного набора идентификаторов.

6. Безопасность. Не запускать найденные EXE, скрипты, установщики и команды из реестра. Анализ должен быть статическим.

7. Управляемые привилегии. Пользовательский режим — по умолчанию; административный — отдельный, с явным запросом. Необходимые разрешения должны определяться конкретным источником.

8. Отчёт о полноте. Показывать не только число найденных программ, но и число недоступных каталогов, ошибок, пропущенных источников и файлов, оставшихся вне области сканирования.
