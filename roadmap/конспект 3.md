### A. Command Registry с контрактами операций

Каждая операция должна быть самостоятельной сущностью.

Например:

Python

Run

```
{
    'operation_id': 'service.restart',
    'executable': 'sc.exe',
    'action': 'restart',
    'target_type': 'service',
    'risk_tier': 'CONTROL',
    'requires_elevation': True,
    'preconditions': [
        'service_exists',
        'restart_allowed',
    ],
    'postconditions': [
        'service_running',
    ],
    'supports_rollback': False,
    'timeout_seconds': 30,
}
```

Это иллюстративная схема, а не готовый контракт для непосредственного выполнения. Реальная операция перезапуска должна учитывать состояние службы, её зависимости, возможность остановки и последствия для работающих приложений.

В реестре стоит хранить также:

* типы и ограничения аргументов;

* источник определения операции и версию контракта;

* требуемые права и допустимый контекст запуска;

* формат результата и классификацию ошибок;

* идемпотентность — безопасно ли повторять команду;

* способ предварительной проверки и проверки результата;

* поддержку отмены или компенсационного действия.

Узлы такого графа должны поддерживать ветвления, параллельное выполнение независимых проверок, тайм-ауты, повторные попытки и ручное подтверждение опасных действий.

### C. Снимки состояния и журнал изменений

Предлагаю завести отдельную подсистему `StateSnapshots`.

Она должна уметь:

1. Сохранять состояние объекта до изменения.

2. Фиксировать команду, аргументы, инициатора, время и результат.

3. Снимать состояние после выполнения.

4. Строить diff.

5. Формировать план восстановления.

6. Проверять, что восстановление действительно вернуло нужное состояние.

Важно: снимок не гарантирует откат. Например, запуск остановленной службы можно отменить остановкой, но отправку сетевого запроса или удаление данных не всегда возможно обратить. Поэтому `supports_rollback` и `compensation_strategy` должны описывать реальные возможности операции, а не обещать универсальный Undo.

### D. Связь процессов с источниками запуска

Для мониторинга Windows я бы добавил отдельный `ProcessProvenance` — сбор происхождения процесса.

Он должен связывать:

* PID и время создания процесса;

* PPID и данные родительского процесса;

* командную строку и путь к исполняемому файлу;

* службу, задачу планировщика или другой известный источник запуска;

* подпись файла и сведения о его издателе;

* сетевые соединения и относящиеся к процессу события ETW.

PID может повторно использоваться после завершения процесса. Поэтому в БД лучше идентифицировать экземпляр процесса комбинацией PID и времени создания, а не одним PID.

Это позволит выяснять, почему в Диспетчере задач отображается множество процессов одного приложения, кто их породил и какие события предшествовали росту нагрузки.

### E. Политики безопасности для AI-агента

LLM не должна самостоятельно определять, какие команды разрешено выполнять. Она предлагает план, а независимый исполнитель проверяет его по реестру и политике.

| Уровень       | Принцип выполнения                                                                        |
| ------------- | ----------------------------------------------------------------------------------------- |
| `OBSERVE`     | Чтение состояния и инвентаризация                                                         |
| `DIAGNOSE`    | Диагностика, трассировка и тесты с ограничениями                                          |
| `CONTROL`     | Управляющие действия с проверкой предусловий                                              |
| `ADMIN`       | Повышенные права и подтверждение по политике                                              |
| `DESTRUCTIVE` | Явное подтверждение, предварительный план и защита от ошибочной цели                      |
| `RECOVERY`    | Отдельная проверка целевого состояния, доступности резервной копии и риска восстановления |

Критически важно: уровень риска нужно назначать конкретной операции и её аргументам. Даже чтение некоторых системных данных может требовать специальных прав, а обычная команда изменения может оказаться опасной при неправильном целевом объекте.

## 4. Как распределить ответственность между LangChain, FAISS и SQLite

Для твоего проекта я бы сохранил следующее разделение.

LangChain / LangGraph — планирование

Разбор задачи пользователя, выбор подходящего диагностического сценария, вызов инструментов через контролируемые интерфейсы, обработка результатов и ветвление workflow.

FAISS — семантический поиск

Поиск описаний команд, документации, известных инцидентов и диагностических процедур. FAISS предлагает релевантные материалы, но не решает, разрешено ли выполнение команды.

SQLite — структурированное состояние

Реестр операций, типизированные параметры, политики, workflow, история выполнения, снимки конфигурации, ссылки на события и агрегированная телеметрия.

Execution Engine — реальное исполнение

Проверка аргументов, разрешений и предусловий; запуск команды; тайм-аут; сбор stdout/stderr; проверка результата; аудит; обработка ошибок и компенсация.

Для уже существующей `telemetry.db` я бы не стал немедленно менять схему или переносить все данные в новую БД. Сначала определил бы границы транзакций и частоту записи. Реестр и историю workflow можно хранить отдельно, если это упрощает миграции и конкуренцию между писателями; связь с телеметрией делать через идентификаторы и временные интервалы.

## 5. В каком порядке внедрять

1. Нормализовать Command Registry. Разбить утилиты на конкретные операции, описать аргументы, права, риски и результаты.

2. Добавить StateSnapshots и аудит. Научиться фиксировать исходное состояние, изменения и результаты.

3. Построить детерминированный Workflow Engine. Сначала реализовать сценарии без LLM, чтобы гарантировать воспроизводимость.

4. Связать workflow с `telemetry.db` и ETW. Добавить временную корреляцию процессов, событий, нагрузки и административных действий.

5. Подключить FAISS и LangChain/LangGraph. Использовать поиск и LLM для формирования планов, но сохранять проверку исполнения в обычном коде.

6. Добавить политики и тестовый режим. Dry-run, оценку последствий, обязательные подтверждения и тесты отката.

Мой главный приоритет: сначала реализовать реестр операций, граф зависимостей и исполнитель с проверкой результата. Именно они превратят каталог системных утилит в управляемую платформу администрирования Windows. LangChain и FAISS затем добавят интеллектуальный поиск и планирование, а не будут заменять механизмы безопасности и управления состоянием.
